## 第十六轮：性能研究——渐进分片渲染落地，content-visibility 实测改 opt-in

- **调研**（对齐大厂 + 参考 GitHub 一年内技术）：GitHub 2026-09《Improving site performance
  by shipping more CSS》——github.com 全站从 CSS-in-JS 迁到 CSS Modules，SSR -55%、组件
  初始化 -25%，理念是"渲染成本从运行时 JS 移回平台 CSS"。大厂对标：Element Plus
  TableV2 / antd rc-virtual-list 都是 JS 窗口化虚拟表格（DOM 会被裁剪）。
- **实验一（content-visibility: auto + contain-intrinsic-size）**：新建
  `styles/virtual.{ts,module.css}`（阈值 30 行），接入 Table/Tree/Select，playground
  万行压测页浏览器实测（M 系列芯片）：列对齐无误、滚动条高度全程稳定（452375px）、
  滚动帧率持平；**但首渲染 2.4s vs 关闭 1.6s——约三成劣化**（每行 containment 记账）。
  结论：本机硬件 + 简单文本单元格下无收益，**改为 opt-in**（`virtual` 默认 false），
  低端设备/复杂单元格/超长弹层场景再开。真实瓶颈其实是 Vue vnode/patch（10k 行 ~1.6s）。
- **实验二（渐进分片渲染，真突破）**：MochiTable 新增 `progressive`（默认开，>30 行生效）：
  先渲染首块 200 行尽快出屏，其余行 requestIdleCallback 分片补齐（jsdom 无 rIC 退化为
  setTimeout 16ms），DOM 最终全量保留（可 Ctrl+F）。**块大小指数翻倍封顶 1600**——
  等大小追加会对既有列表做 keyed diff，近似平方级（200/块 8.8s 只到 6800 行），
  指数块摊薄成线性后 5.4s 补齐 10000 行。实测：**首屏 99-313ms vs 全量 ~2400ms（约 8-24 倍）**。
- **坑三枚**：① jsdom 里 TransitionGroup(tag="tbody") 的行不一定挂在 tbody 下，
  测试行数断言用 `tr[style]`（行带 --_i 变量）别用 `tbody tr`；② 基准测试冷热要分离，
  先跑的组吃 JIT 冷启动亏（首轮 A/B 误判 cv 无开销，补测预热组才现形）；③ 浏览器
  evaluate 里选择器引号会被序列化转坏，用单引号 + 从特征元素 closest 定位（v-show 隐藏节
  里的同款组件会干扰 querySelector 第一命中）。
- **测试**：`src/virtual.spec.ts` 10 用例（阈值助手/cv opt-in 三组件/分片初始 200/补齐到
  全量/progressive=false/阈值内不分片），全套 **134 测试全绿**，typecheck 三包过。
- playground 新增"万行压测"节（1w 表格 + 1k 选项 Select + 2466 节点树 + 双开关 A/B +
  首屏耗时读数），`MOCHI_PORT=5174 ./Mochi.command start` 可看。
